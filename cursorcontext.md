# Контекст проекта: Parsing VK Posts + Analytics

## Назначение
Парсер постов ВКонтакте: скачивает фото, текст, GIF и собирает ссылки на видео из стены сообщества. Токен API — в `.env` (`ACCESS_TOKEN`).

## Точки входа
- **`run_main.js`** — настройки запуска парсера (groupId, offset/count, лимиты по дате, флаги). В конце вызывает `main.js` через `spawn` с CLI-аргументами.
- **`main.js`** — оркестратор парсинга. Получает стену пакетами, предварительно определяет точные границы батча, сохраняет до 6 постов параллельно и полностью ожидает их перед следующим `wall.get`.
- **`main_utils.js`** — переиспользуемая логика CLI, дат, безопасных имён, нормализации `copy_history`, классификации вложений, условий остановки и ограниченного пула асинхронных задач.
- **`network.js`** — вызовы VK API и загрузка изображений с timeout, проверкой HTTP/JSON/MIME/размера и retry/backoff.
- **`run_analityc.js`** — настройки аналитики (группа, режимы, размер выборки). В конце вызывает `analityc.js` с CLI-аргументами.
- **`analityc.js`** — оценка объёма контента группы и/или скачивание случайной картинки. Параметры из CLI.

```

node run_main.js
```

## Важные особенности
- Один `wall.get` получает `startCount` постов. Ответ сначала последовательно проверяется для точной остановки по дате/allCount/опросу, затем выбранные посты сохраняются пулом до 6 параллельных задач; фото внутри поста также загружаются параллельно.
- Результаты GIF/video сливаются после завершения пула в порядке стены, поэтому скорость выполнения задач не меняет порядок ссылок.
- Конец стены: пустой `items` или `nextOffset >= response.count`. Короткий батч (`items.length < count`) сам по себе не конец — VK так бывает на скрытых/удалённых постах.
- Следующий offset после батча: `batchOffset + requestedCount` (не `items.length`), иначе на коротких батчах появляются дубли на стыках.
- Все записи выполняются через Promise и временный файл + rename. На Windows/OneDrive при `EPERM` существующий целевой файл сначала удаляется, затем временный ставится на его место. Явный `process.exit()` не используется, чтобы не оборвать I/O; ошибки завершают процесс через `process.exitCode = 1`.
- Любой непустой текст сохраняется полностью. Имена файлов содержат `owner_id + post.id`; `copy_history` обходится на всю доступную глубину.
- GIF отделяются от прочих документов, video-ссылки включают `access_key`, опросы сохраняются с вариантами и итогами.
- `ACCESS_TOKEN` передаётся VK в POST-теле, не в URL. Временные API/сетевые ошибки повторяются с backoff.
- Session содержит папку `Контент`, списки ссылок и точный checkpoint offset. Название группы не дублируется как вложенная директория.

## Ожидание завершения парсера (для агента)
**Не ждать по русским фразам** в логе («до указанной даты», «успешно завершилась» и т.п.) — ложные срабатывания и срывы при сообщении пользователя в чат.

Надёжные способы (по приоритету):
1. **Foreground:** `Shell` → `node run_main.js` с `block_until_ms` ≥ ожидаемого времени (напр. `600000`). Инструмент сам ждёт **exit** процесса; после возврата — CursorNotify.
2. **Background + статус:** `block_until_ms: 0`, затем проверка завершения shell, либо конец хода и системный notification о завершении.
3. **Pattern только запасной:** единственный надёжный маркер в stdout — ASCII-строка `PARSER_EXIT` (не `exit_code` в footer — он pattern’ом не матчится).

После успеха слать CursorNotify.

## Логи парсера (`main.js`)
- **Обычный режим** (`bool_isinfoShow=false`): старт, 1 строка на пост (`иконка № дата типы`), 1 строка итога батча (offset, даты, счётчики, прогресс по стене), ошибки, финальная сводка сессии + путь Session + `PARSER_EXIT ok`.
- **Подробный** (`bool_isinfoShow=true`): имена сохранённых файлов, URL video/gif, редкий «ждём загрузки», интервал между запросами.
- Не ждать завершения по русским фразам в логе — см. раздел выше.
